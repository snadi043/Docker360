INTRODUCTION:
This project main focus is to build multiple small backend "NODE" projects which deals with REST API's and
which are capabile of communicating with each other.
The small projects included in this application (DOCKER_KUBERNETES_NETWORKING) are as follows
    - USERS_API (This project has node REST API's dealing with creating users and storing them without any database dependency.)
    - AUTH_API (This project has node REST API's dealing with user authentication using tokens and authorization headers and authorizes users by handling the request coming from USERS_API project.)
    - TASKS_API (This project also has node REST API's letting the users to create tasks by which can be treated as a frontend to the USERS_API project but this runs independently from other two projects.)
      The TASKS_API talks to the AUTH_API to verify the token access which identifies the users with verified tokens to perform the actions like "CREATING THE TASKS & FETCHING THE TASKS".

GOAL:
The main motive of this application is to create a project which mainily focuses on networking in between all the three small projects when placed them in a kubernetes world and depending upon DOCKER for 
creating the images and remote repositories.

STEPS IN BUILDING THE APPLICATION:
- First, starting with creating the each individual small projects and create the dockerfiles, docker images and dockerhub repositories for them.
    - USERS_API & - TASKS_API  
      -- First installing all the dependencies needed to build the USERS_API application.
      -- The dependencies include EXPRESS, BODY-PARSER and AXIOS.
      -- Write all the api's needed for the application with defined "endpoints" with the server-name as the hostname, so that docker can detect and manages the applications (user_api & auth_api) listen on
         the same port and build a network between them so that they can communicate with each other.
      -- Write the dockerfile for the application to configure the application with docker to create images and containers.
- Finally, create a docker-compose.yaml file to make it simple for creating the images and containers for all the three small projects and handling them with simple docker-compose commands.
- Commands used:
                                docker compose up --build
                                docker compose down

- Once, the main structure / skeleton for the three small projects are created, it is now time to jump into the individual small projects and create the kubernetes environment for them and 
  enable them with dockerhub images to identify the changes and replicate the changes in the pods within kubernetes containers.
- Firstly, starting with "users_api" project
- Create a deployment and service file which are confined to the "users_api" project.
- Create a dockerhub repository to this project alone.
- Push the changes using the docker image with the tag name.
- Apply the deployment and service yaml files to the "users_api" kubernetes project.

Once the first small project "USERS_API" is all done executing with docker and kubernetes and checking the functionality of the REST API's of the project in postman, it is then the time to work on
next small project which is "AUTH_API". 
As the main project "DOCKER_KUBERNETES_NETWORKING" one of the core motive is to build the "internal pod communication", the project "AUTH_API" has to be setup in a way that it can communicate to
the previously build small project "USERS_API".

- Before jumping into the "AUTH_API" project, it is important to refactor the endpoints in the "USERS_API" project beacuse now, the emphasis is to build the dependency between the two applications.
- In the kubernetes world, if two containers has to communicate with each other and which are in the same pod the "keyword" to be used is "localhost" as the hostname in the endpoints.
      
      So, in the docker-compose file the environment variable is set to AUTH_ADDRESS=auth
          in the kubernetes users-deployment file the environment variable is set to AUTH_ADDRESS=localhost

- Now, since the changes are made in the "users_app" file the application has to be rebuild with docker image and pushed to the repository.
- The same is the case with docker inorder to build the network between two containers and in this case the environment variables can be used to register the hostnames in the docker-compose file.
- For the "AUTH_API" project first, create a remote dockerhub repository and build the image for the individual project.
- Tag the image to the remote dockerhub repository and push the changes.
- Now, inorder to create a pod internal communication there is no requirement to create a new deployment.yaml file for the "auth_api" project instead add a new container with the docker image in the
  "user_api" deployment.yaml file.

Now, two main small projects "USERS_API" & "AUTH_API" are created and configured to achieve the concepts of "POD INTERNAL COMMUNICATION" in both kubernetes and docker platforms, now it is time to
  seperate both the containers to achieve the concept of "COMMUNICATION BETWEEN THE PODS".
In the realtime, it is a good practise that every single application is build in an individual pod to keep the maintainance and functionality of the application simple and scalable.
So, now in this case, the "USERS_API" & "AUTH_API" projects has to be seperated for which, since in the previous steps the deployment and the service yaml files are created for the "USERS_API" project,
  in this step it is time to create sepereate deployment and service yaml files for "AUTH_API" project.
The important refactoring that has to be done in this process is mainly, keeping the "AUTH_API" private, which is not meant to be "public facing". So the type of the service for "AUTH_API" is to be changed
  to "CLUSTERIP", which has the ability to provide the Loadbalancing to some extent and can provide the static IP address and also make the service private to the cluster.
Also, the ports of the "AUTH_API" project has to be changed as per the application. 
Other important changes include, removing the "AUTH" container from the "USERS_API" container because now these two applications are no more running on the concept of "PODS INTERNAL COMMUNICATION".
  So, a new service for the "AUTH_API" project has to be created along with a new deployment yaml file, where the "AUTH" container has to be created which is removed from the "USERS_API" project.

Now, to create the communication between the pods, there are three main ways where the containers with the proper environment variables has to be mapped.
 - Knowing the IP address of the application through the service and placing it in the environment variable.
 - Utilizing the feature of Kubernetes provided automatic IP Address generation which is accessible through an specific environment variable in a format which is all CAPITALS, seperated by _ and adding the 
   SERIVCE_HOST to the end of the environment variable. So, the format is "<NAME_OF_SERVICE>_SERVICE_HOST".
 - The last method of creating the "PODS COMMUNICATION" is using the Kubernetes provided feature called "CORE DNS", Domain Network Service, which provides us with the namespaces using which the services can be
   identified within the cluster in kubernetes environment and the format to be used is "<NAME-OF-SERVICE>.<NAMESPACE-NAME>". If you dont have any namespace assigned to the service, the "default" is the value 
   to be used.
